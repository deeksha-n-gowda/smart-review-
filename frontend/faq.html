A five-step code review process

Finding vulnerabilities early is cheaper than finding them in production. This is the process Smart Review is built to support — each step catches a class of bug that the previous one misses.

1. Scan every file automatically

Start with static analysis over the whole codebase. It costs minutes rather than days and reliably finds the mechanical defects: unparameterised SQL, secrets committed to source, weak hashes, path traversal, unsafe deserialisation. Upload a folder of .py, .java, .cs and .js files and every one of them is analysed.

2. Triage by severity, not by order

Sort findings into critical, high, medium and low. A single exploitable SQL injection matters more than ten naming nits, so fix critical and high issues before you read anything else. Smart Review ranks each finding automatically and gives every file its own risk score so you can see at a glance where the real exposure is.

3. Read the explanation, not just the alert

A finding without context is noise. For each vulnerability Smart Review shows the exact flagged line, a plain-English description of the flaw, and the feature attribution behind the score. If the attribution shows the finding was driven by a pattern that does not apply in your context, you can dismiss it with a reason instead of guessing.

4. Fix and verify

Apply the suggested fix — parameterised queries instead of string concatenation, environment variables instead of hardcoded secrets, SHA-256 instead of MD5 — then re-run the analysis on the changed file. The review page has a Re-analyze button for exactly this loop.

5. Add the human layer

No scanner finds missing authorisation, incorrect business logic or a dependency you trusted too much. Automated analysis gives you a reliable baseline; human review is what catches design flaws. Use the machine results to spend human attention where it matters.

What Smart Review detects, by language

Each language has its own rule set, so the findings are specific to the language's real weaknesses rather than generic regex noise. A project can mix languages; every file is analysed on its own.

Python Python rules

  • SQL injection via string concatenation and via .format()
  • OS command injection and subprocess shell injection
  • Code injection through eval() and exec()
  • Insecure deserialisation with pickle and unsafe YAML loading
  • Weak cryptographic hashes (MD5, SHA-1) and insecure random usage
  • Hardcoded secrets and credentials
  • Path traversal, Flask debug mode enabled
  • Bare except clauses, mutable default arguments
  • High cyclomatic complexity, long functions, string concatenation in loops
  • Debug leftovers: print() statements and TODO/FIXME comments

Java Java rules

  • SQL injection
  • Hardcoded passwords and credentials
  • Insecure deserialisation
  • Weak random number generation (non-cryptographic Random)
  • Null pointer dereference risk
  • printStackTrace() in production code
  • Empty catch blocks
  • TODO/FIXME comments

C# C# rules

  • SQL injection
  • Hardcoded connection strings and credentials
  • Insecure deserialisation via BinaryFormatter
  • Weak cryptography (MD5/SHA1)
  • Path traversal
  • XSS via Response.Write()
  • Empty catch blocks
  • TODO/FIXME comments

JavaScript JavaScript rules

  • Cross-site scripting via innerHTML and document.write()
  • Dangerous eval() usage
  • Sensitive data stored in localStorage
  • Prototype pollution risk
  • Hardcoded API keys and secrets
  • Insecure postMessage target origin
  • console.log() left in production code
  • === vs == comparisons
  • TODO/FIXME comments

How severity and risk scores work

Every finding is assigned one of four severities, and every file receives a risk score between 0% and 100% that rolls up its findings.

SeverityMeaningExample
Critical Directly exploitable; fix before any release. SQL injection from concatenated user input
High Serious risk; fix in the current cycle. Hardcoded credentials, weak hashing
Medium Needs attention but not immediately exploitable. Empty catch blocks, debug leftovers
Low Code-quality and maintainability issue. TODO comments, long functions, loose equality

The per-file risk score is what powers the dashboard, so you can spot the project most likely to cause an incident before you open a single line of it.

Why explainable AI matters for code review

A score without a reason is a black box, and developers rightly distrust black boxes in their security tooling. Smart Review uses two established explainability methods so you can interrogate every result.

SHAP — why does this file score so high?

SHAP (SHapley Additive exPlanations) splits a prediction across the features that produced it. For a file-level risk score, each bar represents one contributing pattern — hardcoded secrets, injection risk, complexity, unused error handling — and its length shows how much it moved the score. The result is a ranked list of what actually drove the risk.

LIME — why was this exact line flagged?

LIME (Local Interpretable Model Explanations) works locally. For a single finding it inspects the code around the flagged line and shows which nearby constructs pushed that finding's confidence up. It answers the narrower question a developer asks while staring at one line of code: why this one?

What this means in practice

When a finding looks wrong, you can see the reason instead of guessing. The attribution charts in the analysis panel let you distinguish a genuine injection risk from a pattern that merely looks similar — and, crucially, they let you justify the finding to the rest of your team.

Frequently asked questions

What is AI code review, and how is it different from a manual review?

A manual review is limited by time and attention, and rarely checks every branch of every function. AI code review applies the same rule set to every file consistently. It does not replace a human reviewer — it removes the mechanical work so the reviewer can focus on architecture, business logic and trade-offs. Smart Review gives you both: a machine-checked baseline plus an explanation of why each finding matters.

How do I find security vulnerabilities in my code before release?

Start with static analysis on every file to catch injection flaws, hardcoded secrets, weak cryptography and dangerous API usage before the code runs. Then add a layer of human review for the bugs a scanner cannot see, such as missing authorisation checks and insecure design. Smart Review automates the first step and explains the results, so you can focus manual review on what genuinely needs a human. Fix critical and high severity findings first.

Which programming languages does Smart Review support?

Python (.py), Java (.java), C# (.cs) and JavaScript (.js, .mjs) are supported today. Each language has its own rule set and parser: Python is analysed with its AST and pylint, Java with javalang, and the C# and JavaScript analysers use dedicated pattern and structure checks. You can mix languages inside the same project, and each file is scored independently.

What does "explainable AI" mean here — what are SHAP and LIME?

A black-box risk score is not actionable. Smart Review shows why a file was scored that way. SHAP attributes the risk score across the individual features that produced it, and LIME explains each finding locally by examining the exact lines around the flagged code. SHAP gives the file-level picture, LIME gives the line-level reason. Both are in the Detail tab of the analysis panel.

Is my source code secure? What happens to the files I upload?

Your source code is encrypted at rest with AES-256-GCM before it is written to the database, so the stored blob is not readable as plain text. Analysis runs on the encrypted-at-rest copy and the decrypted content is only materialised in memory while a file is being scanned. You can delete a project at any time.

How long does an analysis take, and can I review multiple files at once?

A typical single file is analysed in a couple of seconds, and a project with many files is processed file by file so one slow file never blocks the rest. The review page gives you a tab per file, so you can compare the source, risk score and vulnerability list for each file without leaving the page. The URL updates as you switch, so a link to one specific file's analysis can be bookmarked or shared.

Can I share or export the analysis results?

Yes. Use the Export button in the review toolbar to produce a clean, print-ready report you can save as a PDF or share with your team. The report contains the file summary, the risk score and the full list of findings with their explanations.
